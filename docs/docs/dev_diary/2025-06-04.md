## 1. Config Loader

### 1.1. Implementação 

Um carregador de configurações descrito em
`./backend/harvest/harvest/config_loader.py`. Ali temos um `dataclass` definido
assim: 

```python
@dataclass(slots=True, frozen=True)
class SourceConfig:
    """
    Data class representing the configuration for a single data source.
    """
    type: str
    region_name: str
    ttl_days: int
    url: str
    args: dict[str, Any]
```

Ele é a classe que armazena as informações de configuração da fonte.

A seguir temos o `ConfigLoader` em si. Ele abre uma conexão com o db
`harvest_config` e procura pela collection `sources` e `source_types`. Para
isso, ele usa um wrapper do motor. A ideia é pegar todas as configurações
disponíveis na coleção e ler uma a uma, mapeando-a para uma lista de
`SourceConfig`. A docstring da definição da classe abaixo:

```python
class ConfigLoader:
    """
    Loader class for fetching and validating source configurations from MongoDB.

    Args:
        config_client (MongoClientWrapper): A wrapper around the MongoDB client
        to access configuration collections.

    Methods:
        load() -> list[SourceConfig]:
            Load and validate all sources, returning a list of SourceConfig
            instances.
    """
```

O principal motivo para essa abstração é poder definir objetos de tipo de
configuração, em que podemos facilmente adicionar ou modificar as definições de
acesso a algumas de nossas fontes. Exemplo do openweather:

```json
{
  "_id": {
    "$oid": "6840ecb24759654dd9cf5e98"
  },
  "type": "openweather",
  "url": "https://api.openweathermap.org/data/3.0/onecall",
  "required_args": [
    "lat",
    "lon"
  ]
}
```

A partir dessa definição de tipo, podemos definir um objeto para cada região na
outra coleção. Exemplo para Santo André:

```json
{
  "_id": {
    "$oid": "6840eb644759654dd9cf5e95"
  },
  "type": "openweather",
  "region_name": "Santo André",
  "ttl_days": 7,
  "args": {
    "lat": -23.667548,
    "lon": -46.528934,
    "units": "metric"
  }
}
```

### 1.2. Testes

Eu não acredito que focar em cobertura de testes faça muito sentido. Prefiro
criar uma lista de requisitos básicos para o código e criar testes para
garantir que esses requisitos estão sendo cumpridos. Então lá vai (com uma
ajudinha do GPT):

✅ Requisitos de funcionamento

1. Carregar todos os documentos da coleção `sources`.
2. Carregar todos os documentos da coleção `source_types`.
3. Para cada `source`:

   * Validar se o `type` existe em `source_types`.
   * Validar se todos os `required_args` estão presentes.
   * Ignorar e avisar se faltar algo.
4. Retornar uma lista apenas com `sources` válidos.
5. Avisar via *log* se um `source` for inválido.
6. Permitir conexões assíncronas (`async/await`).
7. Fechar a conexão com o banco corretamente.

---

🧪 O que será testado

1. Carregamento vazio: nenhuma fonte → lista vazia.
2. Fonte válida → objeto `SourceConfig` correto.
3. Fonte com tipo inexistente → ignorada com aviso.
4. Fonte faltando argumentos obrigatórios → ignorada com aviso.
5. Fonte com argumentos extras → aceita.
6. Mistura de válidas e inválidas → só válidas na lista.
7. Argumentos obrigatórios `None` ou vazios → tratado como falta → ignorado.
8. `ttl_days` customizado → respeitado no resultado.
9. Chamada concorrente de `load()` → resultados consistentes.

### 2.2. Testes

✅ Requisitos de funcionamento

1. **SourceBase**
   1.1 Classe abstrata; não pode ser instanciada diretamente.
   1.2 Propriedades de conveniência `.type` e `.region` refletem o
`SourceConfig`.
   1.3 Método assíncrono abstrato `harvest()` **retorna um `dict[str, Any]`**
(não mais um iterável).

2. **OpenWeatherSource**
   2.1 Exige a variável de ambiente **`OPENWEATHER_API_KEY`**; se ausente ⇒
`HarvestError`.
   2.2 Constrói a URL usando todos os pares de `src_config.args` (ignorando
valores `None`) + `appid`.
   2.3 Usa `httpx.AsyncClient` com o `timeout` fornecido.
   2.4 Em resposta HTTP **2xx** devolve **um único dicionário** contendo:
   \- JSON original da API **e** campos adicionais (`dt_request`,
`region_name`, `type`).
   \- O JSON **deve** conter obrigatoriamente `lat`, `lon`, `timezone` e
`hourly`; se faltar qualquer um ⇒ `HarvestError`.
   2.5 Erros HTTP **4xx/5xx** ⇒ `HarvestError` (mensagem inclui código).
   2.6 Erros de rede/timeout (`httpx.RequestError`) ⇒ `HarvestError`.
   2.7 Ignora pares cujo valor seja `None` ao montar os parâmetros.
   2.8 Respeita o `timeout` configurado.
   2.9 Campo `dt_request` é timezone-aware e truncado para o início da hora
(`minute==second==microsecond==0`).
