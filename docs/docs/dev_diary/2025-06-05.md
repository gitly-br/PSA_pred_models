## 1 Harvester

### 1.1. Implementação

O que faz o harvester:

1. Instancia uma classe `Harvester`. Veja o docstring dela abaixo.
```python
class Harvester:
    """
    Harvester loads all configured sources and handles the data harvesting.

    On initialization:
      - It prepares a Mongo client (MongoClientWrapper)
      - It loads all source configurations using ConfigLoader
      - It builds a list of concrete SourceBase instances (e.g.,
        OpenWeatherSource)

    Methods:
      - harvest(): iterates over all sources, calls their harvest method,
        inserts the result into the MongoDB collection named by type and region.

    Example collections:
      - "openweather_sao_paulo"
      - "openweather_santo_andre_tam_central" (if subregion exists)

    Summary of harvest() result:
      {
        "openweather": {"inserted": 10, "skipped": 2, "failed": 1},
        ...
      }
    """
```

2. Implementa os método `_build_source` e `build_congigs` que transforma cada
   objeto de configuração em uma `SourceBase` concreta. A escolha da abstração
    aparece aqui como uma injeção de dependência. Para facilitar na hora de
    instanciar o Harvester, vou deixar um dicionário que mapeia keywords para
    implementações concretas. Caso a keyword não exista, ele lança um
    `NotImplementedError`.
```python
    async def _build_configs(self) -> list[SourceConfig]:
        """
        Loads all source configurations from MongoDB.
        """
        loader = ConfigLoader(self.mongo)
        configs = await loader.load()
        return configs

    def _build_source(self, cfg: SourceConfig) -> SourceBase:
        """
        Maps a SourceConfig to its concrete SourceBase implementation.
        """
        if cfg.type == "openweather":
            return OpenWeatherSource(cfg)
        raise NotImplementedError(
            f"Source type '{cfg.type}' is not implemented."
        )
```

4. A classe também implementa o harvest, que itera na lista de fontes
   concretas, chama o método harvest da fonte, pega o payload de resposta e
   adiciona em uma coleção de acordo com o nome da região e tipo da fonte (e.g.
   "Santo André" vai para "opw_santo_andre_all"). Caso haja subregião, ela é
   adicionada ao final do nome da coleção (e.g. "Tam Central" vira
   "opw_santo_andre_tam_central")
```python
    async def harvest(self) -> dict[str, dict[str, int]]:
        """
        Harvests data from all sources and inserts into appropriate MongoDB
        collections.

        Returns:
            A dictionary summarizing the number of inserted, skipped, and
            failed operations per source type.
        """
```

### 1.2. Testes

✅ Requisitos de funcionamento do **Harvester**

1. **Carregamento de configurações**

   * Deve buscar todas as configurações via `ConfigLoader.load()` (async).
   * Cada `SourceConfig` vira uma instância concreta de `SourceBase` através de
   um mapa `{tipo → classe}`; tipo desconhecido ⇒ `NotImplementedError`.

2. **Nome da coleção**

   * Para cada payload usa o padrão:
     `"<source_type>_<slug(region_name)>"` (p. ex. `openweather_sao_paulo`).
   * Se existir sub-região (campo opcional), deve ser concatenada após o slug
   principal.

3. **Pipeline por fonte**

   1. Chama `source.harvest()` → recebe **um dict**.
   2. Chama `mongo.ensure_indexes()` com `dedup_key="dt_request"` e `ttl_days`
      vindo do `SourceConfig`.
   3. Usa `mongo.insert_one_safe()`:

      * retorno `0` ⇒ inserido.
      * retorno `1` ⇒ duplicado (skipped).

4. **Resumo final** (`dict`)

   ```python
   {
     "openweather": {"inserted": X, "skipped": Y, "failed": Z},
     ...
   }
   ```

   * Contadores iniciam em zero por tipo.
   * `failed` incrementa se `source.harvest()` levantar `HarvestError`; o loop
   continua.

5. **Erros de infraestrutura**

   * `HarvestError` não derruba o serviço; apenas registra no resumo.
   * Qualquer exceção fora do fluxo previsto deve ser propagada.

6. **Chamadas assíncronas corretas**

   * `get_data_collection()` **não** deve ser aguardado.
   * `ensure_indexes()` e `insert_one_safe()` **devem** ser aguardados
   (`await`).

## 2. CLI

Por fim, precisamos de uma cli simples para ser o ponto de entrada do módulo.
Aqui não vale a pena fazer nada muito rebuscado. Simplesmente instancia um
harvester, um mongo wrapper e faz o harvester ler todas as fontes cadastradas e
gravar no banco com TTL de 7 dias.

A única decisão importante aqui foi criar dois handlers do logger para que os
logs de `error` e `warning` usem `stderr`. Com isso, é possível rodar a cli
assim:

```sh
python -m harvest.cli 2>> log.txt
```

E ter um log textual que recebe append sempre que um skip ou um failure
acontece na leitura das fontes. Ideal? Não, mas é um começo.
