# Início do refactor do projeto
*Escrito em 29-05-2025 por Nicola*

Iniciado o refactor do projeto PSA

Escopo dessa modificação:

* Modularizar o projeto, separando os scripts de coleta de dados do backend do
modelo;
* Adicionar documentação ao repositório do projeto;
* Criar uma estrutura para que exista *cache* de inferência em vez de rodar o
modelo toda vez que o usuário acessa a interface;
* Adicionar ferramentas de orquestração para garantir robustez do sistema;
* Adicionar ferramentas de monitoramento para ter log e notificações de quedas
do sistema.

Abaixo, um rascunho inicial da nova arquitetura

<center><img src={NewArch} /></center>

Comecei adicionando uma documentação com docusaurus e estilizando com as cores
da gitly. A ideia é ter essa entrada de diário para eu não me perder no
desenvolvimento em dias não consecutivos. A seguir, configurei um pipeline do
Github actions para fazer o deploy dessa documentação no Pages e ficar
disponível online. Nada disso requer qualquer menção ao código necessário. É um
yaml simples que está disponível em `.github`, na raíz do repo. A princípio, o
deploy está na branch `refactor` para testes. Após estabilizar a primeira
versão do sistema novo, essa documentação deverá ser integrada na branch `main`

A seguir, o foco recai sobre uma estrutura nova de diretórios para o
repositório:

```
├── backend
│   ├── distill
│   ├── floodcast
│   └── harvest
├── deploy
├── docs
│   ├── docs
│   ├── node_modules
│   ├── src
│   └── static
├── frontend
│   ├── assets
│   ├── pages
│   └── static
└── notebooks
16 directories
```

A ideia é criar uma modularização completa do ambiente de desenvolvimento.

* O backend cuida dos serviços de dados
    * floodcast é o serviço principal de predição de enchentes. Ele expõe
    modelos através de uma API
    * harvest é o coletor de dados de diversas fontes para colocar em um banco
    nosql (possivelmente com um TTL baixo)
    * distill é um serviço que pega os dados crus coletados pelo harvest e
    destila eles em arquivos parquet para consumo dos notebooks de treinamento.
* O frontend abriga a página que consome a API do floodcast e exibe os
resultados para o usuário
* Em notebooks ficam os notebooks usados para treinamento e exploração de
datasets.
* A pasta deploy abriga os arquivos necessários para fazer o deploy do sistema.

Algumas outras condições de contorno:

* Cada subserviço deve ter seu próprio Dockerfile, de modo que as imagens são
totalmente independentes.
* Para o desenvolvimento da aplicação, utiliza-se o docker-compose unificado na
raíz do repositório
* O ambiente de desenvolvimento utilizará pods do kubernettes, tendo um arquivo
yaml para cada serviço a ser lançado
    * Ainda sobre o ambiente de desenvolvimento, vão ser dois: dev e prod. A
    ideia é poder ter um canário para testar a aplicação completa antes de
    colocar em produção
    * Deve haver integração entre o github com o saveincloud usando esteiras de
    deploy. Essas esteiras serão baseadas nas branchs main e dev. Para que isso
    seja possível, provavelmente será necessário usar Terraform
* Não vou aplicar TDD, mas cada módulo construído vai ter testes de
funcionalidade básicas para que possamos modificá-los no futuro com alguma
segurança de que a funcionalidade básica não foi quebrada.

Muitas coisas ainda estão incertas ou mal definidas, mas esse desenho geral da
arquitetura e configuração do repositório nos permite ir para o desenvolvimento
do primeiro módulo: o *harvest*.
